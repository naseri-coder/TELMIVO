# TELMIVO v0.2.0 Release Readiness

This runbook defines the evidence required to declare the R4 source checkpoint ready for
a separate release/production-preparation decision.

## Candidate identity

The authoritative candidate is the exact R4G HEAD. All required checks must refer to that
same commit. Results from an ancestor do not validate a later candidate.

## Mandatory checks

1. R4 v0.2.0 Release Readiness — static auditor and native reusable workflow.
2. CI Go — gofmt, vet, unit/contract race tests, command builds and native integration.
3. CI Web — npm install, lint, typecheck, unit tests, build and browser smoke.
4. Security Baseline — source scanner, govulncheck and npm high-severity audit.
5. Build Images — backend/Mini App images, media tools, non-root identity and synthetic
   Compose startup.
6. Production Readiness — production configuration/preflight, image build and non-root
   validation.
7. CodeQL — required only when repository capability/policy enables the job; a policy-driven
   skip must be documented and must not be described as a successful scan.

## Native matrix

The disposable native gate uses PostgreSQL 17, Redis and NATS JetStream. It must apply all
23 migrations from a fresh database, execute the R4B–R4F integration journeys plus R4G
continuity tests, execute the R4 browser matrix, perform a fresh backup into a separate
PostgreSQL 17 restore service and execute all phase recovery assertions plus the R4G
cross-feature recovery matrix.

No production database, real Telegram charge, real payment provider or real customer
credential is authorized by this runbook.

## Blocking rules

Release readiness is BLOCKED when any mandatory job is queued indefinitely, fails before
runner/step allocation, fails a test, is cancelled, or is missing. Repository-owned failures
must be corrected on R4G and revalidated on the new exact HEAD. External runner failures
must not be converted into a source PASS.

## After PASS

A clean source PASS only authorizes a separate decision about merge/tag/release preparation.
Production deployment, real migrations, DNS/network changes, secret provisioning and
customer traffic require their own explicit authorization and operational checklist.
