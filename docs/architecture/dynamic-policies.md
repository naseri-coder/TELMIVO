# R2A shared policy contracts

Official entry sources identify the same Telegram account and call `identity.Enter` inside a transaction. Only server-validated Telegram transports may supply an identity. Source records discovery, never identity ownership. Mini App authentication accepts signatures from configured official bot credentials. Synthetic mode does not make an unverified browser user ID trusted. Customer bots are not official identity issuers.

`policy_versions` extends existing plans, features, flags and plugins; it does not replace their catalogs. Typed, validated immutable version bodies cover TRIAL, QUOTA, RESOURCE, GRANT, PRICE, OFFER and PAYWALL. Workspace versions use FORCE RLS; global configuration is readable by the trusted application, but administration APIs require the relevant granular permission. New permissions are not automatically granted to all existing administrators; configured owner login explicitly provisions them.

Trials are enrollment snapshots, not plans. Eligibility, trigger, subject scope, once behavior, parallel/keep-first stacking, fallback, bundle, dates and duration are stored configuration. Enrollment uniqueness spans versions and bots. PER_USER trials follow that user's identity; PER_WORKSPACE/PER_GROUP/PER_INSTALLATION have explicit subject IDs. Group claims require a verified administrator result from a Telegram authority adapter, workspace permission and a globally unique Telegram group ID. No transfer/reclaim operation is provided. Settings persist after access expiry. Production authority adapters and full bot operations remain deferred.

Runtime authorization, quota reservation, official bot access integration and admin Preview use `policies.Resolve`. Global flags, plugin status/dependencies, workspace permission and explicit feature overrides retain their precedence. Trial/grant sources cannot bypass them. Preview allows a simulated plan but never writes subscription state; runtime endpoints and reservation reject simulated-plan inputs. Preview uses the selected user's actual workspace role. The compatibility resolver defaults to the workspace owner when no actor is provided; request authorization passes the actual user.

Resource policies distinguish item size, cumulative usage, retained capacity and concurrent work. Units are COUNT, BYTES, STORAGE_BYTES, SECONDS, JOBS, CONCURRENT_JOBS, REQUESTS, TOKENS and CREDITS. Transferred bytes and stored bytes use separate metrics. Calendar windows use IANA timezones, Monday weeks and local month/day boundaries. Rolling usage counts committed reservation history within the configured interval, including a failure only when its recorded policy charges failure. Changing calendar granularity reuses committed and pending reservation history within the new interval. Capacity and concurrency never reset by calendar.

Commercial combination: plan metric → recorded trial bundle(s) → effective grant/add-on bundles → workspace resource override → infrastructure cap. Each amount declares ADD/MAX/MIN/REPLACE. Parallel grants have deterministic recorded/key order; conflicting same-priority metric definitions are rejected. Capabilities are registry keys with their own workspace permissions. Offers are configuration references, not purchased entitlements: only an authorized explicit GRANT/ADDON assignment supplies access. Price amounts are integer strings with the existing asset scale. Offers reference a fixed immutable price version; current prices do not rewrite that reference or invoices.

Reservations lock the workspace quota aggregate, retain a stable operation fingerprint and policy version, and count pending allocations. Completion commits durable usage once; failure/cancellation releases it unless the snapshot charges failure. Concurrency allocations are released on either terminal outcome. Expired reservations stop blocking new work; successful settlement after expiry fails closed. Calendar reservations also expire at the window boundary, preventing a late job crossing into a separately allocated period. Future long-running product adapters must budget job timeout/expiry and supply all authoritative byte/time/count measurements; R2A does not implement ingestion, retention cleanup or lease renewal.

Infrastructure caps are read-only to the runtime database role and commercial UI. Changing an absolute cap requires a separately reviewed infrastructure migration. No commercial grant can remove one. PostgreSQL owns configuration, enrollment and durable consumption; no Redis policy cache is introduced.

Admin Mini App `/plans` supplies lightweight plan/plugin controls, versioned trial/quota/resource/grant/price/offer/paywall editors and server Preview. Advanced bundle configuration uses a labeled JSON editor plus simple duration/limit/window fields. Read-only controls explain missing authority; ordinary users can view their plans but cannot administer global policy. Bulk active-trial rewrite, full permission-management UI, advanced pricing/offer workflows and complete product UIs are deferred.
